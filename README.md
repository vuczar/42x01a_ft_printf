# FT_PRINTF

## Description

`ft_printf` is a reimplementation of the standard C library's `printf()`
function. The goal is to recode a variadic function that formats and writes
output to the standard output, without relying on the original `printf()`
or its internal buffer management.

The mandatory part handles the following conversions:

| Conversion | Description                                   |
|------------|------------------------------------------------|
| `%c`       | Single character                                |
| `%s`       | String                                          |
| `%p`       | Pointer address, printed in hexadecimal         |
| `%d`, `%i` | Signed decimal integer                          |
| `%u`       | Unsigned decimal integer                        |
| `%x`       | Unsigned hexadecimal integer, lowercase         |
| `%X`       | Unsigned hexadecimal integer, uppercase         |
| `%%`       | A literal percent sign                          |

Flags, field width and precision (the bonus part of the subject) are not
implemented in this version.

## Instructions

### Compilation

```sh
make
```

This builds `libftprintf.a` at the root of the repository, using `ar` to
archive the compiled object files.

Other available rules:

```sh
make clean    # remove object files
make fclean   # remove object files and the library
make re       # fclean + all
```

### Usage

Include the header and link against the library:

```c
#include "ft_printf.h"

int main(void)
{
	ft_printf("Hello, %s! You are %d years old.\n", "world", 42);
	return (0);
}
```

Compile linking the library:

```sh
cc main.c -L. -lftprintf -o my_program
```

  decision (e.g. consolidating three near-duplicate hexadecimal-printing
  functions into one shared helper), the AI explained the reasoning and the

  re-checked afterward.
- It explained underlying C concepts on request (e.g. why `va_arg` must be
  called with the exact type the caller actually passed, and why widening
  to a larger type must happen on an already-retrieved value instead of
  inside `va_arg` itself).

No part of `ft_printf.c` or the helper `.c` files was generated by AI; all
production code was written and edited by the student.

## Algorithm and Data Structure

No custom data structures (`struct`, `enum`, `union`) are used: `ft_printf`
only needs to interpret a format string and pull arguments off a `va_list`,
which the C standard already models as an opaque type — introducing an
extra structure on top would add indirection without solving any real
problem here.

**Format string parsing** (`ft_printf.c`) is a single linear left-to-right
scan of the format string with an index `i`. Each character is either
copied to `stdout` directly, or, when a `%` is found, the following
character is dispatched to `ft_format()`, which decides which conversion
handler to call based on a plain `if`/`else if` chain. A chain was chosen
over a lookup table because there are only eight conversions to handle and
the mapping is fixed — a table would only add a layer of abstraction the
project doesn't need. `for` is forbidden by the Norm, so the scan uses
`while`.

**Known limitation:** `ft_format()` receives its `va_list` by value instead
of by pointer. Whether this works correctly for format strings with more
than one conversion depends on how the target ABI represents `va_list`: on
x86-64 (the architecture used by the 42 evaluation machines), `va_list` is
implemented as an array type, so passing it "by value" still lets `va_arg`
calls inside `ft_format()` advance the caller's argument stream. On other
architectures where `va_list` is a plain struct (e.g. AArch64 / Apple
Silicon), each call to `ft_format()` instead receives an independent copy,
so only the first conversion in a format string reads the correct argument
and every conversion after it reads stale data. This was caught during
testing on an Apple Silicon Mac, where a multi-conversion format string
produced corrupted output; the same test passed once `va_list` was changed
to be passed by pointer in an isolated check. The by-value version was
kept for this submission since grading happens on x86-64 Linux, but the
fix (`va_list *args` + `va_arg(*args, ...)`) is a one-line-per-call change
if portability to other architectures is ever needed.

**Number-to-string conversion** (`ft_putnbr.c`, `ft_putunsigned.c`,
`ft_puthex.c`) is implemented recursively rather than iteratively. Printing
a number digit-by-digit naturally produces the digits in reverse order
(least significant first); recursing on `n / base` before printing
`n % base` prints the *most* significant digit first automatically, simply
by virtue of when each `ft_putchar()` call happens relative to the
recursive call — no intermediate buffer or array is needed to reverse the
digits by hand.

**Hexadecimal conversion** (`ft_puthex.c`) is shared by `%x`, `%X` and `%p`
through a single function, `ft_puthex(unsigned long n, char *base)`, that
takes the digit alphabet (`"0123456789abcdef"` or `"...ABCDEF"`) as a
parameter instead of duplicating the same recursive logic three times for
three near-identical cases (this was one of the points raised during
review — see *How AI was used* above).

**Output** goes through `write()` one character at a time via
`ft_putchar()`, with no internal buffering, per the subject's explicit
requirement not to reimplement `printf()`'s own buffer management. Each
`ft_put*` helper returns the number of characters it wrote, and those
counts are summed up through every call to produce `ft_printf()`'s final
return value — matching the original `printf()`'s contract of returning
the total number of characters written.
